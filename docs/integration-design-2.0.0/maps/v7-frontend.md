| Element | Text | Behaviour |
|---|---|---|

Connection pill (`applyState`, FE:832-834):

- `#dot` class: `dot` (red, not connected) / `dot ok` (green + halo, connected) / `dot sim` (amber, simulator).
- `#portName`: `st.port` when connected to hardware; `simulator` when `simulated`; otherwise `st.last_error || "not connected"`.
- On SSE error: dot red and `Streaming interrupted` (FE:827).

`reconnect()` (FE:870-877): toast `Reconnecting...` → `POST /api/reconnect` (no body, raw `fetch`, not logged) → toast `Connected <port>` or `Connection failed` (error style) → always calls `connectStream()` again. On HTTP 503/500 the JSON has only `detail`, so `r.connected` is undefined and the user sees only `Connection failed`; the backend's reason text is not displayed.

`stopEverything()` (FE:864-869): `POST /fn/motors.stop_all {}` → toast `Stopped all motors, syringe pumps, weight readings and closed solenoid valves`. Errors are swallowed here (the generic error toast from `call()` still shows).

Keyboard (FE:879-881): `Escape` anywhere → `preventDefault()` + `stopEverything()`. This is the only keyboard binding.

## 6. How live state arrives

### 6.1 Transport

`connectStream()` (FE:812-828): one `EventSource("/api/stream")`. Each message is `data: {"type": ..., "data": ...}` (main.py:200-201). The server sends a full state snapshot as the first message, then events; a comment ping `: ping` every 15 s (main.py:182-192). The page has no reconnect logic of its own apart from the `Reconnect` button (it relies on the browser's EventSource auto-retry); `es.onerror` only shows `Streaming interrupted`.

| `type` | Origin | Handler |
|---|---|---|
| `state` | every `STATE,…` line from the firmware, and scale stop errors (transport.py:275-313, 224-226) | `applyState(msg.data)` |
| `weight` | every `WEIGHT,…` line, 10 Hz (transport.py:246-271) | `applyWeight(msg.data, true)` |
| `log` | every tx/rx serial line `{t, kind, text}` (transport.py:382-387) | log card; also scale-offline detection |

### 6.2 State snapshot fields (transport.py:97-110) and which ones the page uses

```
connected, simulated, port, last_error      -> header pill, connection tile
cleaning (bool)                             -> cleaning card + locking
motors: { "<groupId>": {selected, state} }  -> tiles, group status tile, cleaning text
valves: { "<id>": bool }                    -> Linkage valve tile
pump:   { online, syringe_ul }              -> syringe pump tile, syringe size
scale:  { grams, raw, stable, online, stream_hz, updated, sequence }
                                            -> only stream_hz is read from state (0 => offline alert)
firmware                                    -> not shown
```

Motor state strings seen by the page: `idle`, `wait`, `run`, `move` (FE:837). State is per **group**, not per motor.

### 6.3 Weight sample (`applyWeight`, FE:719-736)

Uses `grams`, `raw`, `stable`. Updates `#wVal` (to `display_decimals`, default 3), stable colouring, `#wRaw`, badge `stable` / `Changing`, turns the live dot on, hides the alert, updates the `weight` status tile, pushes into `wData` (max `chart_points` = 300), recomputes stats and redraws the chart — on every sample.

### 6.4 Scale offline (`weightOffline`, FE:737-740)

Triggered by (a) an SSE log line starting `ERR,stream_stopped` or `ERR,timeout` (FE:824) or (b) a state with `scale.stream_hz === 0` (FE:859). Effect: live dot off, alert bar shown, badge `No response`.

Consequence worth knowing: `motors.stop_all` deliberately sends `W,STREAM,0` (motors.py:524-525), so **after every “stop all” the scale card shows the “Weight module did not respond” alert** and the operator has to press `Restart reading` (a later weight dose restarts the stream by itself, motors.py:369-373). The same alert shows whenever the Arduino is not connected (initial `stream_hz` is 0).

### 8.2 Enabling / locking (`renderMotor` FE:482-493, `renderCleaning` FE:360)

| Situation | Disabled | Still enabled |
|---|---|---|
| No motor selected in the group | `Forward rotation`, `reverse`, `quantitative revolution`, `Quantitative number of reverse revolutions`, `weighs to` | tiles; `■ Stop` (acts as stop-all) |
| `STATE.cleaning` true (server state, so it applies to every open console) | all motor tiles, `Forward rotation`, `reverse`, both dose buttons, `weighs to`, **the per-group `■ Stop`**, `Start cleaning` (text `Cleaning in progress...`) | `■ stop all`, Esc, syringe pump card, scale card |
| `doseBusy[gid]` true (browser-local flag, set only for the duration of the HTTP call in `doseMove`) | that group's tiles, `Forward rotation`, `reverse`, dose buttons, `weighs to`; `Start cleaning` | that group's `■ Stop`; the other group's controls |
| `gravimetric_dose.enabled` false | `weighs to` | — |

Points the implementers should know:

- `doseBusy` protects a **weight dose** for its whole duration, because that HTTP call blocks until the dose ends. For a **volume dose** the call returns as soon as the `P,…` command is acknowledged, so the flag is cleared almost immediately and the buttons are enabled again while the pump is still turning (group state `move`). The page does not lock on `state === "move"` or `"run"`.
- `doseBusy` lives only in that browser tab. A second tablet, or the same tab after a refresh, shows the buttons enabled during a weight dose; the backend is the real guard: `motor N is weighing and quantifying; please stop or wait for it to complete` (select / run / dose / clean, motors.py:106-109) and `motor N is using the weight module for quantification` (second weight dose, motors.py:337-339).
- During cleaning the backend also rejects select / run / stop / dose with `Automatic cleaning is being executed; please wait for completion or click ”Stop All”` (motors.py:112-114).
- Stopping a weight dose: `■ Stop` of that group (`motors.stop` cancels it, motors.py:265) or `stop all`. The pending `dose_by_weight` call then fails with `Weighing and rationing has been stopped by the user` (shown as an error toast).

### 8.3 Confirmation dialogs

None. The page contains no `confirm()`, `alert()`, `prompt()` or modal. Cleaning, tare, calibration (overwrites `config/scale_calibration.json`), syringe initialisation and reverse dosing all fire on a single tap.

### 8.4 Errors and feedback

- Single toast at the bottom centre (`toast(msg, err)`, FE:208-212): visible 2.8 s; a new toast replaces the old one; red variant for errors. Long-running operations therefore lose their "in progress" message after 2.8 s (only the disabled buttons remain as a hint).
- `call()` (FE:221-236): network failure → toast `Unable to connect to the backend service`, log `network error:<msg>`, rethrow. HTTP not OK → message = `body.detail` (FastAPI) or `statusText`; toast (error) + log `✗ <name>:<detail>`; throw `Error(detail)`.
- Status codes from `main.py:157-163`: 400 = `FunctionError` (parameter validation, interlocks); 503 = `LinkError` (`Not connected yet Arduino`, `command timeout(<cmd>)`, or the firmware's raw `ERR,…` line, transport.py:323-357); 500 = other, as `ExceptionType: message`.
- Several handlers do not catch the rethrown error (`jog`, `stopMotor`, `doseMove`, all pump and scale buttons): the toast is shown, and the browser additionally logs an unhandled promise rejection. `selectMotor`, `startCleaning`, `stopEverything`, `refreshPump`, `loadSeries` swallow it.

## 10. `docs/architecture.html`

Header (ARCH:81-83): `system architecture` — “browser Until → FastAPI rear end(four independent function modules)→ USB → Arduino Mega → four subsystems”, “All pins and conversion coefficients are only written in `config/hardware.yaml` a place”.

### 10.1 Why a backend exists (§1, ARCH:92-101)

The earlier version opened the COM port from the browser (Web Serial). Three problems listed: a COM port can be opened by only one program; data lived only in the tab; a browser is unsuitable for long automation (“, we need to connect the plasma spectrum and run the optimization algorithm.”). Conclusion: “browser is just one of the clients” — Python scripts, a later ML loop or another PC can use the same HTTP API.

### 10.2 Four layers (§2, ARCH:103-185)

```
Browser  frontend/index.html (single file)
   |  POST /fn/<function>, GET /api/config          ^ GET /api/stream (SSE: state + weight + Record)
Backend  FastAPI (Python, on the lab PC)
   main.py      routing,No device knowledge When
   registry.py  FaaS Registry + parameter verification
   transport.py The only owner of the serial port + state cache
   config.py    read hardware.yaml + pin check
   functions/motors.py (relay + peristaltic pump) | firmware valve linkage (motor 2 / 9 automatic control) | functions/pump.py (syringe pump) | functions/scale.py (weight module)
   |  USB serial port 115200 ‧ One instruction per line
Arduino Mega 2560  firmware/Arduino/Arduino.ino
   8 peristaltic pump (D2~D9 relay, 2 × DM542J) | 2 solenoid valve (D10 / D11, ULN2803A → relay)
   syringe pump (Serial1 D18 / D19, RS485 ASCII) | weight module (Serial2 D16 / D17 + D36, RS485 Modbus RTU)
```

Responsibility table (ARCH:175-185): front end = screen, touch operation, curve (knows no pins or command format); router = HTTP, SSE, dispatch (knows no device); function modules = unit conversion, parameter checks, building commands (touch neither serial nor HTTP); transport = open port, read lines, match replies, state cache, broadcast (does not know what a mL is). Caption: “Each floor only talks to the adjacent floor below.”.

### 10.3 "FaaS" functions (§3, ARCH:187-212)

Each action is a registered function with described parameters, so “Verification, files, and front-end prompts share the same definition.”. Endpoints: `GET /fn` (list of functions, parameters, ranges) and `POST /fn/<Name>` (JSON object in, `{ok, result, elapsed_ms}` out). Example call: `curl -X POST http://127.0.0.1:8000/fn/motors.dose … -d "{\"motor\":3,\"volume_ml\":2,\"flow_ml_min\":24}"`. Note (ARCH:210-212): “This is not true serverless” — the functions live in one long-running process because the serial port must be held permanently.

### 10.4 "IaC" configuration flow (§4, ARCH:214-267)

`config/hardware.yaml` is “The only source of truth” feeding three consumers:

- backend — read by `config.py` at start, checks for duplicate pins — “The service will take effect as soon as it is reopened”
- front end — `GET /api/config` (cards, slider limits, buttons) — “The rearrangement will take effect”
- firmware — `tools/gen_firmware_config.py` generates `hw_config.h` — “needs to be re-burned to take effect”

`selftest.py` compares `hw_config.h` with the YAML.

| Changed | To do | Takes |
|---|---|---|
| flow coefficient, valve name, flow frequency | restart backend, refresh page | seconds |
| foot position (D2~D9, valves, RS485) | `python tools/gen_firmware_config.py` → reflash with Arduino IDE → restart backend | about a minute |
| `link.port` | restart backend | seconds |

Warning (ARCH:265-267): duplicate pins are refused at start-up; the service will not start and names the two conflicting entries.

### 10.5 Two data flows (§5, ARCH:269-329)

1. Command, downwards (request/response): browser `POST /fn/motors.dose` → registry validates (“Refund if the traffic limit is exceeded. 400”) → `motors.py` converts (“motor 2-9 Sharing coefficient; 40 mL/min → 2825 step/Second”) → Arduino line such as `P,3,1000,200`.
2. Measurement, upwards (push): Arduino `WEIGHT,12.34,…` at 10 Hz without being asked → transport background thread (updates cache + ring buffer) → SSE `GET /api/stream` → browser (big number + curve).

Stated properties: history is kept in the backend, so a refresh or a second tablet shows the same curve; several consoles can be open at once and see the same live data.

Closed-loop weight dose (ARCH:327-329): 5 baseline samples → continuous run at 40 → 10 → 3 mL/min; slow down at 2 g remaining, trim speed at 0.5 g remaining; stop when the reading enters target ± 0.5 %; then 7 stable samples for the final error. “Weighing timeout, weight failure and global stop will interrupt the process. ”

### 10.6 File map (§6, ARCH:331-360)

`run.bat` (one click: build environment, generate firmware config, start service, open browser), `selftest.bat`, `config/hardware.yaml`, `backend/{main,config,registry,transport,simulator}.py`, `backend/functions/{motors,pump,scale}.py`, `frontend/index.html`, `firmware/Arduino/{Arduino.ino,hw_config.h}` (`hw_config.h` is generated — “Please do not modify it by hand”), `tools/{gen_firmware_config,url,selftest}.py`, `docs/*.html`.

### 10.7 How the author intended a new device to be added (§7, ARCH:362-374)

The example used is literally the plasma spectrometer (“Take the plasma spectrum that will be connected later as an example.”). Three steps, “There is no need to change a single line of the existing file.”:

1. add a `plasma:` section to `config/hardware.yaml` (IP, port, integration time…),
2. add `backend/functions/plasma.py` with `@function("plasma.acquire", …)`,
3. import it in `backend/functions/__init__.py`.

`GET /fn` then lists the new functions automatically; “To make a spectrum card on the screen, you need to use the front end. ”

### 10.8 Operating rules written for the operator (§8, ARCH:376-386)

| Task | How |
|---|---|
| Start the day’s experiment | double-click `run.bat`; the browser opens the console |
| End | `Ctrl+C` in the black window |
| Emergency stop | the red button at the top right of the console, or `Esc` |
| Change Arduino of USB port | press “Reconnect”; if still not found, set `link.port: COM5` in the YAML |
| There is no hardware and I want to see the interface. | set `link.simulate` to `true` |
| After changing the settings, I want to make sure it’s not broken. | double-click `selftest.bat` |
| To burn firmware | **stop the service with Ctrl+C first**, then open Arduino IDE |

Console address: `http://127.0.0.1:8000` (DOCS:115; hardware.yaml:21-22).

### 10.9 Warnings and troubleshooting (ARCH:314-316, §9 ARCH:388-400)

- One COM port, one program: while the backend runs, close the Arduino IDE serial monitor, and vice versa; stop the service before flashing.
- `run.bat` window flashes and closes → the batch file was saved with LF; cmd needs **CRLF**, and the batch files are kept **pure ASCII** on purpose (Chinese messages are printed by Python).
- Console says “cannot connect to the backend service” The chemical substance → is the `run.bat` window still open?
- Top right shows “not connected” → USB cable; Arduino IDE serial monitor holding the port; set `link.port`; press “Reconnect”.
- command timeout → firmware version; boot banner should be `READY,arduino+pump+2valves+scale`.
- Orange alert on the weight card → module not answering; see the scale wiring page, then `POST /fn/scale.diagnose {"mode":"scan"}`.
- Motor does not move, no error → driver ENA polarity, relay click, 24 V on.
- Pin conflict at start → message names the two; fix YAML, regenerate `hw_config.h`, reflash.

## 13. Observations that matter for the merge (facts, not design decisions)

1. The V7 console is generated from `/api/config`; its motor groups, labels, limits and cleaning times are data from `hardware.yaml`. A merged UI that re-implements these cards should keep reading them from config, not copy today's numbers.
2. The full set of pump-side operations the operator has today is section 5's table. Anything the merged UI drops from that list removes a capability; anything it adds (e.g. manual valves) does not exist in V7.
3. The V7 page has **no password, no operator identity, no confirmation dialogs, no text inputs**. An operator password is entirely new relative to V7.
4. Stop semantics in V7: `■ stop all` / Esc → `motors.stop_all` stops peristaltic pumps, syringe pump, valves **and the weight stream**; the scale card then shows its "no response" alert until `Restart reading`. The per-group stop is disabled during cleaning. A unified stop button needs to account for both.
5. Locking is partly client-local (`doseBusy`) and does not cover a running volume dose or continuous run. The server-side `cleaning` flag is the only lock shared by all consoles.
6. Live data depends on SSE (`/api/stream`) with three event types; the weight curve history is kept by the backend (6000 samples) and the page shows 300.
7. V7's author already described how plasma functions were meant to be added to this backend (ARCH §7): YAML section + `backend/functions/plasma.py` + one import.
8. V7's backend is FastAPI/uvicorn on `127.0.0.1:8000` (main.py:22-24, 226-230). The EC project instructions state its bundled PC Python is the embeddable build with the standard library only and no pip, and its UI is on `127.0.0.1:8766`. How the merged program gets FastAPI/uvicorn/pyserial/yaml (or avoids them) is outside the files I was assigned; flagged for whoever reads the V7 backend and packaging.
9. V7 visual style is dark, large touch targets, card grid; whether it resembles the original HMI style is for the HMI readers to judge. The owner asked for the original HMI's style, so V7's look is a source of controls and wording, not necessarily of styling.

## 14. Could not determine from these files

- What the firmware does when a new `S`, `V` or `P` command arrives for a group that is in `move` (volume dose in progress). The page allows it and the backend does not reject it. *Answer: nothing is refused (Arduino.ino:222-264). `S` for the motor that is moving does nothing; `S`, `V` or `P` for another motor of that group stops the dose at once, with no error, and switches the relay; `V` or `P` for the same motor aborts the dose and starts the new run. ### Further additions (not in the text above)

- **Success toasts for the syringe pump do not mean the pump obeyed.** `has sent initialization`, `Inhalation N µL`, `launched N µL`, `Syringe pump has stopped` and the valve highlight are shown whenever the HTTP call returns 200. The backend returns 200 for any `PUMP,…` line, including `error=7` (The device is not initialized) or `error=9` (Piston overload); the page never reads `result.lines`. The pump's reply is visible only as a green line in the log card.
- **The `syringe pump` status tile lags.** It follows `state.pump.online`, which changes only when a `STATE` line arrives. After `detection` succeeds the toast says `Syringe pump is connected` while the tile can still read `Not yet detected` until some other action produces a `STATE` (`pump.detect` sends no `?`, `pump.py:54-57`).
- **A volume dose can be cut short from the same page without any warning** (see the first answer in §14): the dose and jog buttons, and the other tiles of the group, are enabled again as soon as `motors.dose` returns, while the pump is still turning.
- **`Quantitative number of reverse revolutions` on motor 2 or 9 opens the linked valve as well** — the firmware's valve sequence does not depend on direction (`Arduino.ino:253-260`).
- **Weight dose stop point.** The toast `Complete X g,error ±Y g` uses `error_g = dispensed − target`, where `dispensed` is the median of 7 readings taken 5 s after the pump stopped. The backend stops the pump as soon as the median gain reaches `target − 0.5 %` (`motors.py:414`), not at the target itself; the red style appears only when the final value is outside ±0.5 %.
- **What the page needs from a replacement backend,** if these cards are re-implemented on another server: the six plain routes, the 22 functions with the result fields listed in section 5, and SSE messages `{"type": "state" | "weight" | "log", "data": …}` with the state shape of section 6.2. Nothing else.
